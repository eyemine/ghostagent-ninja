# ERC-8226 Compliance — RAMS Principal Preservation in GhostAgent

## Overview

ERC-8226 (Responsible Agent Management Standard — RAMS) defines the **principal** as the human (or legal entity) that is ultimately liable for the actions of an autonomous AI agent. It separates three concerns that are often conflated in naive agent deployments:

| Concept | Address | Role |
|---|---|---|
| **Principal** | `principalOf[tokenId]` | Human liable for agent actions (ERC-8226) |
| **NFT Owner** | `ownerOf(tokenId)` | Holder of the identity key (may be delegated) |
| **TBA** | `accountOf[tokenId]` | ERC-6551 executor — signs transactions on behalf of the Safe |
| **Safe** | `safeOf[tokenId]` | Treasury vessel — holds funds and modules |

The critical invariant: **principal ≠ executor**. A Molt changes the executor (TBA) but never changes who is liable.

---

## How GhostAgent Implements RAMS

### 1. Principal Set at Registration

When `register()` is called on `GhostRegistry`, the caller (`msg.sender`) is immediately recorded as the principal:

```solidity
// ERC-8226: set principal to msg.sender (the human who registered)
principalOf[tokenId] = msg.sender;
emit PrincipalSet(tokenId, msg.sender);
```

This is the **only** time the principal is set automatically. Every subsequent change requires an explicit call to `setPrincipal()` by the current principal — it cannot be changed by the NFT owner, the Safe, or the TBA.

### 2. Molt Preserves Principal

The `molt()` function creates a new TBA and swaps it into the Safe as the sole owner. The `principalOf` mapping is **intentionally untouched**:

```solidity
/// @dev Principal is intentionally NOT changed — molting preserves responsibility
function molt(uint256 tokenId) external {
    require(ownerOf(tokenId) == msg.sender, "Not owner");
    // ... creates newTba, swaps Safe owner to newTba ...
    emit Molted(tokenId, oldTba, newTba, safe);
    // principalOf[tokenId] unchanged
}
```

This means that even if an agent NFT is transferred to a new wallet, the original principal remains on record until they explicitly call `setPrincipal()` to transfer liability. This is intentional: **identity portability does not imply liability transfer**.

### 3. Explicit Principal Transfer

Liability can be transferred, but only by the current principal:

```solidity
function setPrincipal(uint256 tokenId, address newPrincipal) external {
    require(newPrincipal != address(0), "Invalid principal");
    require(principalOf[tokenId] == msg.sender, "Not principal");
    principalOf[tokenId] = newPrincipal;
    emit PrincipalSet(tokenId, newPrincipal);
}
```

This provides a clear, auditable on-chain trail of liability handovers via the `PrincipalSet` event log.

### 4. BYO NFT Principals

For **Bring-Your-Own-NFT** molts (CHONK, POWNFT, ENS, Normies), the principal is recorded off-chain in the Cloudflare Worker KV at molt time:

```
principal:{agentName}  →  ownerWallet (lowercased)
```

The `getAgentIdentity` worker action resolves the principal with this precedence:

```
principal:{name} KV override  >  nftmailgno controller  >  null
```

This mirrors the on-chain resolution logic: explicit override wins, then the minting controller, then null.

## Events

```solidity
event PrincipalSet(
    uint256 indexed agentId,
    address indexed principal
);
```

All principal assignments and transfers are emitted as `PrincipalSet`. To reconstruct the full liability history for an agent, filter this event by `agentId` on the GhostRegistry contract:

- **GhostRegistry v2:** `0x194f200b2C624e27a14865292d1C50cF46211565` (Gnosis mainnet, chain 100)
- **GhostRegistry v1 (legacy):** `0x73f2f2ef73dc512cac0f5b0372f1d58a84ed13e6`

## Oracle Verification

The `notapaperclip.red` oracle exposes the principal as the **"NFT Owner Wallet"** field in the OSINT Digital Footprint panel. It reads from the Worker KV `principal:` key and falls back to `identityNft.owner`. This is a read-only view — the oracle cannot write or alter principal records.

Independent verification:
```
GET https://notapaperclip.red/api/osint/footprint?agent={agentName}
→ { offChain: { principal: "0x..." } }
```

## Liability Matrix During a Molt

```
Before molt:
  principalOf[1] = 0xAlice   ← liable
  ownerOf(1)     = 0xAlice
  accountOf[1]   = TBA_A     ← executor
  safeOf[1]      = Safe_1    ← treasury

After molt (NFT transferred to 0xBob, then molt called):
  principalOf[1] = 0xAlice   ← still liable (unchanged)
  ownerOf(1)     = 0xBob     ← new key holder
  accountOf[1]   = TBA_B     ← new executor
  safeOf[1]      = Safe_1    ← same treasury

After setPrincipal (Alice calls setPrincipal → Bob):
  principalOf[1] = 0xBob     ← liability explicitly transferred
  event PrincipalSet(1, 0xBob) on-chain
```

This pattern ensures that regulators, counterparties, and oracle systems always have an unambiguous, on-chain answer to the question: **"Who is responsible for this agent's actions?"**
